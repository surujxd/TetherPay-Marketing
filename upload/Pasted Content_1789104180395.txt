### Approved Marketing Copy

**Primary:** Earn in USDT. Spend in INR.  
**Secondary:** Deposit USDT, create an INR payment order, and have the payment fulfilled through TetherPay's verified settlement network.  
**Agent:** Provide INR liquidity. Receive USDT settlement and earn commission.

- "Guaranteed payments"
- "Zero risk"
- "Anonymous"
- "Bank-account protection"

- "RBI approved" / "FIU registered" / "SEBI authorized" (unless actually established)
- Any claim of regulatory license not actually held

## 2. Assumptions & Decisions

| # | Decision | Rationale |
|---|---|---|
| A1 | Single Next.js monorepo with role-based routing | Faster to build, separable later |
| A2 | pnpm as package manager | Faster installs, better workspace support |
| A3 | Node.js 20 LTS | Stable, supported, matches Netlify defaults |
| A4 | Supabase Auth for all authentication | Reduces external service dependencies |
| A5 | Central USDT wallet model (not per-user wallet) | Matches stated business requirement |
| A6 | Manual payment verification first (no automated chain monitoring) | Matches stated business model |
| A7 | PostgreSQL numeric(38,18) for all financial amounts | Safe decimal precision |
| A8 | HALF_UP rounding on displayed/settled amounts | Standard financial rounding |
| A9 | Supabase Realtime via PostgreSQL replication | Free tier compatible |
| A10 | Telegram as notification-only, not authorization | Security boundary |
| A11 | TRON (TRC-20) as primary USDT network | Lowest fees for USDT transfers; others configurable |
| A12 | UPI as sole INR payment method | Matches stated product scope |
| A13 | 1-level referral depth for financial rewards | Anti-MLM requirement |
| A14 | Orders expire after 10 minutes (configurable) | Backend-controlled, configurable |
| A15 | All sensitive files in Supabase private buckets | Security requirement |
| A16 | No direct balance field mutations from frontend | Ledger-only financial state |

## 3. Business Model

### 3.1 Operational Flow

```
CUSTOMER
    │
    │  deposits USDT to central wallet
    ▼
CENTRAL TETHERPAY USDT WALLET
    │
    │  manager manually verifies on-chain
    ▼
CUSTOMER INTERNAL USDT LEDGER (credited)
    │
    │  customer creates INR payment order
    │  (USDT reserved from available balance)
    ▼
PAYMENT ORDER MARKETPLACE (AVAILABLE state)
    │
    │  agent views and claims order
    ▼
AGENT
    │
    │  agent pays recipient via own UPI channel
    │  (agent uses personal INR funds)
    ▼
UPI RECIPIENT (payment received in INR)
    │
    │  agent submits: UTR / reference / screenshot
    ▼
MANAGER
    │
    │  manually verifies payment
    ▼
    ├── REJECTED → order re-enters marketplace or refunded
    └── APPROVED
           │
           ▼
    AGENT USDT SETTLEMENT
    (reimbursement + commission credited to agent wallet)
           │
           │  agent requests USDT payout
           ▼
    ADMIN/TREASURY
    (manual USDT transfer to agent's external wallet)
```

### 3.2 Revenue Model

```
Customer pays:   INR amount + platform fee (converted to USDT debit)
Agent receives:  USDT equivalent of INR paid + commission
Platform earns:  Spread between customer rate and agent rate + fees - commissions
```

### 3.3 Central Wallet Model

```
Customer A ─┐
Customer B ─┼──▶ Central TetherPay USDT Wallet (single address per network)
Customer C ─┘
```

- Customers send USDT to the **central wallet address**.
- Customers submit a deposit request with TX hash.
- Managers verify on-chain and approve/reject.
- The application's internal ledger is the source of truth for individual balances.

### 4.3 Financial Arithmetic

**NEVER use JavaScript native `number` or `float` for financial amounts.**

All financial calculations use `decimal.js`:

```typescript
import Decimal from 'decimal.js';

Decimal.set({ precision: 38, rounding: Decimal.ROUND_HALF_UP });

// Agent settlement example
function calculateAgentSettlement(inrPaid: string, agentRate: string, commissionRate: string) {
  const inr = new Decimal(inrPaid);
  const rate = new Decimal(agentRate);
  const commission = new Decimal(commissionRate).div(100);

  const baseUsdt = inr.div(rate);
  const commissionInr = inr.mul(commission);
  const commissionUsdt = commissionInr.div(rate);
  const totalUsdt = baseUsdt.add(commissionUsdt);

  return {
    baseUsdt: baseUsdt.toFixed(8),
    commissionInr: commissionInr.toFixed(2),
    commissionUsdt: commissionUsdt.toFixed(8),
    totalUsdt: totalUsdt.toFixed(8),
  };
}
```

All amounts stored in PostgreSQL as `numeric(38,18)`.

```sql
  amount              numeric(38,18) NOT NULL,
  balance_after       numeric(38,18) NOT NULL,  -- running balance at time of entry

CREATE TABLE account_balances (
  account_id      uuid PRIMARY KEY REFERENCES ledger_accounts(id),
  available       numeric(38,18) NOT NULL DEFAULT 0,
  reserved        numeric(38,18) NOT NULL DEFAULT 0,
  pending         numeric(38,18) NOT NULL DEFAULT 0,
  total           numeric(38,18) GENERATED ALWAYS AS (available + reserved + pending) STORED,
  updated_at      timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT balances_available_non_negative CHECK (available >= 0),
  CONSTRAINT balances_reserved_non_negative CHECK (reserved >= 0),
  CONSTRAINT balances_pending_non_negative CHECK (pending >= 0)
);

-- Balance update function (called by server-side operations only)
CREATE OR REPLACE FUNCTION update_account_balance(
  p_account_id uuid,
  p_available_delta numeric(38,18),
  p_reserved_delta numeric(38,18),
  p_pending_delta numeric(38,18)
) RETURNS void AS $$
BEGIN
  INSERT INTO account_balances (account_id, available, reserved, pending)
  VALUES (p_account_id, 0, 0, 0)
  ON CONFLICT (account_id) DO NOTHING;

  UPDATE account_balances SET
    available  = available + p_available_delta,
    reserved   = reserved  + p_reserved_delta,
    pending    = pending   + p_pending_delta,
    updated_at = now()
  WHERE account_id = p_account_id;

  -- Invariant checks
  IF (SELECT available FROM account_balances WHERE account_id = p_account_id) < 0 THEN
    RAISE EXCEPTION 'Insufficient available balance for account %', p_account_id;
  END IF;
  IF (SELECT reserved FROM account_balances WHERE account_id = p_account_id) < 0 THEN
    RAISE EXCEPTION 'Insufficient reserved balance for account %', p_account_id;
  END IF;
  IF (SELECT pending FROM account_balances WHERE account_id = p_account_id) < 0 THEN
    RAISE EXCEPTION 'Insufficient pending balance for account %', p_account_id;
  END IF;
END;
$$ LANGUAGE plpgsql;
```

```sql
  COALESCE(ab.pending, 0) as pending_usdt,
  ap.total_usdt_earned
FROM profiles p
JOIN agent_profiles ap ON ap.id = p.id
LEFT JOIN ledger_accounts la ON la.user_id = p.id AND la.account_type = 'AGENT_USDT'
LEFT JOIN account_balances ab ON ab.account_id = la.id;
```

## 8. Authentication & RBAC

### 8.1 Authentication Architecture

Supabase Auth is used for all user authentication.

**Client access rules:**
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (anon key): safe for browser
- `SUPABASE_SERVICE_ROLE_KEY`: server-only, never in client code, never prefixed `NEXT_PUBLIC_`

**Session model:**
- Supabase JWTs (short expiry) with refresh tokens
- Server-side session via `@supabase/ssr` middleware
- Cookie-based sessions (httpOnly, secure, sameSite=lax)
- Session stored in encrypted httpOnly cookie

### 8.2 Middleware

```typescript
  if (session && (path.startsWith('/ops') || path.startsWith('/admin'))) {
    // Fetch role from profiles table using service role client
    // Redirect if insufficient role
  }
```

## 9. Ledger & Financial Model

### 9.1 Accounting Model

TetherPay uses a **single-currency double-entry ledger** (USDT only on internal accounts, INR tracked as metadata).

Every financial event creates:
- A `ledger_transaction` (the event descriptor)
- ≥ 2 `ledger_entries` (debits and credits that net to zero)

**Ledger Accounts:**

| Account Type | Owner | Purpose |
|---|---|---|
| `CUSTOMER_USDT` | Customer | Customer available and reserved balance |
| `AGENT_USDT` | Agent | Agent available and pending balance |
| `PLATFORM_REVENUE` | Platform | Platform earnings |
| `PLATFORM_FLOAT` | Platform | Unallocated platform USDT |
| `PLATFORM_RESERVES` | Platform | Reserved/contingency |

### 9.2 Deposit Credit Flow

```
Event: Manager approves deposit of 500 USDT

Ledger Transaction:
  type: DEPOSIT_CREDIT
  reference_type: DEPOSIT
  reference_id: <deposit_id>

Ledger Entries:
  1. CREDIT customer_usdt account +500.000000000000000000
  2. DEBIT  platform_float account -500.000000000000000000
     (represents customer liability on platform)

Account Balance Updates:
  customer.available += 500
```

### 9.3 Order Reserve Flow

```
Event: Customer creates confirmed payment order (₹5,000 at ₹91.50/USDT)
       customer_usdt_debit = 5000/91.50 = 54.6448087 USDT (+ fees)

Ledger Transaction:
  type: ORDER_RESERVE
  reference_type: ORDER

Ledger Entries:
  1. No balance change on platform side
  2. customer_usdt account: available -54.6448087, reserved +54.6448087
```

### 9.4 Order Completion & Agent Settlement

```
Event: Manager approves payment → order completed

Step 1 — Customer debit:
  ORDER_DEBIT
  customer_usdt: reserved -54.6448087 (consumed)
  platform_revenue: +54.6448087

Step 2 — Agent settlement:
  AGENT_SETTLEMENT_CREDIT
  agent_usdt: pending +55.4644808
  platform_revenue: -55.4644808

Step 3 — Commission is included in agent_total_usdt
```

### 9.5 Agent Withdrawal

```
Event: Agent requests withdrawal of 55 USDT

Step 1 — Reserve:
  AGENT_WITHDRAWAL_RESERVE
  agent_usdt: available -55, reserved +55

Event: Admin approves + executes USDT transfer

Step 2 — Debit:
  AGENT_WITHDRAWAL_DEBIT
  agent_usdt: reserved -55 (gone from ledger)
```

### 9.6 Balance Calculation

Balances are **never directly computed from ledger scan at runtime** (slow).  
They are maintained in `account_balances` table updated synchronously in database transactions.

Available balance invariant: `available >= 0` enforced by DB constraint.

### 9.7 Financial Invariants (Enforced)

1. **TX hash uniqueness:** Unique index on `deposits(tx_hash)` where credited.
2. **Order single completion:** Unique index on `agent_settlements(order_id)`.
3. **Order single claim:** Partial unique index on `payment_orders(agent_id)` for active states.
4. **Idempotency keys:** Unique on all create/approve operations.
5. **Balance non-negativity:** DB constraint on `account_balances`.
6. **Double-entry:** Every ledger transaction must have sum(debits) = sum(credits).
7. **No direct balance edits:** RLS prevents direct UPDATE on `account_balances`.

## 10. State Machines

### 10.1 Deposit State Machine

```
CREATED ──────────────────────────────────────────┐
   │                                              │ (customer creates deposit request)
   ▼                                              │
TX_SUBMITTED ◄─────────────────────────────────────┘
   │
   │ (customer submits tx hash)
   ▼
PENDING_VERIFICATION
   │
   ├──── [manager: wrong/suspicious] ────► ESCALATED ──► [senior review]
   │                                              │
   ├──── [duplicate tx hash] ──────────► DUPLICATE      │
   │                                              │
   ├──── [risk system] ─────────────────► RISK_HOLD ◄───┘
   │
   ├──── [manager: reject] ────────────► REJECTED (terminal)
   │
   └──── [manager: approve] ──────────► VERIFIED
                                            │
                                            │ (system credits ledger)
                                            ▼
                                         CREDITED (terminal)
```

**Transitions:**

| From | To | Actor | Validations | Side Effects |
|---|---|---|---|---|
| CREATED | TX_SUBMITTED | Customer | deposit exists, status=CREATED | notification sent |
| TX_SUBMITTED | PENDING_VERIFICATION | System | tx_hash present | ops queue alert |
| PENDING_VERIFICATION | VERIFIED | Deposit Reviewer | checklist complete, not duplicate | — |
| VERIFIED | CREDITED | System | auto after verify | ledger credit, notification, Telegram |
| PENDING_VERIFICATION | REJECTED | Deposit Reviewer | reason required | notification, audit |
| PENDING_VERIFICATION | ESCALATED | Deposit Reviewer | reason required | senior alert |
| PENDING_VERIFICATION | RISK_HOLD | System/Manager | risk flag | risk event, admin alert |
| PENDING_VERIFICATION | DUPLICATE | Reviewer | same tx_hash already credited | audit |

### 10.2 Payment Order State Machine

```
DRAFT
  │ (customer saves incomplete order)
  ▼
QUOTE_CREATED
  │ (rate quoted, expiry set)
  ▼
CONFIRMED
  │ (customer confirms intent)
  ▼
FUNDS_RESERVED
  │ (USDT reserved from customer balance)
  ▼
AVAILABLE ◄──────────────────── (re-enter if agent times out or cancels)
  │
  │ [agent claims]
  ▼
ASSIGNED
  │
  │ [agent submits payment]
  ▼
PAYMENT_SUBMITTED
  │
  ▼
MANAGER_REVIEW
  │
  ├─── [reject] ──────────────► REJECTED ──► (funds released to customer)
  │
  ├─── [dispute] ─────────────► DISPUTED ──► dispute workflow
  │
  └─── [approve] ─────────────► APPROVED
                                    │
                                    ▼
                                 COMPLETED
                                    │
                                    ▼
                            AGENT_SETTLEMENT_POSTED
                                    │
                                    ▼
                            COMMISSION_POSTED (terminal)

AVAILABLE/ASSIGNED + [timer expires] ──► EXPIRED ──► (funds released)
CONFIRMED/FUNDS_RESERVED + [customer cancels] ──► CANCELLED ──► (funds released)
```

**Side Effects Table:**

| Transition | Customer Ledger | Agent Ledger | Notifications | Telegram |
|---|---|---|---|---|
| → FUNDS_RESERVED | available→reserved | — | Order confirmed | — |
| → AVAILABLE | — | — | Order in marketplace | agent broadcast |
| → ASSIGNED | — | — | Agent assigned | agent notified |
| → PAYMENT_SUBMITTED | — | — | Payment submitted | — |
| → COMPLETED | — | — | Payment completed | customer, agent |
| → AGENT_SETTLEMENT_POSTED | — | pending credit | Settlement pending | agent |
| → COMMISSION_POSTED | — | pending→available | Commission credited | agent |
| → EXPIRED | reserved→available | — | Order expired | — |
| → REJECTED | reserved→available | — | Payment rejected | customer |
| → CANCELLED | reserved→available | — | Cancelled | — |

### 10.3 Agent Withdrawal State Machine

```
REQUESTED
  │
  ▼
RISK_CHECK ──── [auto/manual flag] ──► HELD (manual review)
  │
  │ [passes]
  ▼
ADMIN_REVIEW
  │
  ├─── [reject] ─────────────► REJECTED (reserved→available returned)
  │
  └─── [approve] ────────────► APPROVED
                                    │
                                    ▼
                                PROCESSING (treasury initiates tx)
                                    │
                                    │ (tx hash recorded)
                                    ▼
                                  PAID (terminal)
```

## 11. Financial Formulas

All formulas use `decimal.js` in application code and `numeric(38,18)` in database.  
Rounding: `HALF_UP` to 8 decimal places for USDT, 2 for INR.

### 11.1 Customer Quote

```
inr_amount             = customer-specified INR
platform_fee_percent   = settings.platform_fee_percent   (e.g. 0.00%)
platform_fee_flat_inr  = settings.platform_fee_flat_inr  (e.g. 0.00)
customer_rate          = settings.customer_quote_rate     (e.g. 91.50)

platform_fee_inr       = (inr_amount × platform_fee_percent / 100) + platform_fee_flat_inr
total_inr              = inr_amount + platform_fee_inr
customer_usdt_debit    = total_inr / customer_rate
```

**Example:**
```
inr_amount           = 5000
platform_fee_percent = 0%
platform_fee_flat    = 0
total_inr            = 5000
customer_rate        = 91.50
customer_usdt_debit  = 5000 / 91.50 = 54.64480874 USDT
```

### 11.2 Agent Settlement

```
agent_rate         = settings.agent_settlement_rate  (e.g. 91.00)
commission_rate    = agent tier rate                 (e.g. 1.50%)

base_usdt          = inr_paid / agent_rate
commission_inr     = inr_paid × commission_rate / 100
commission_usdt    = commission_inr / agent_rate
agent_total_usdt   = base_usdt + commission_usdt
```

**Example (₹5,000 paid, rate 91.00, commission 1.50%):**
```
base_usdt          = 5000 / 91.00   = 54.94505495 USDT
commission_inr     = 5000 × 0.015  = 75.00 INR
commission_usdt    = 75 / 91.00    = 0.82417582 USDT
agent_total_usdt   = 55.76923077 USDT
```

### 11.3 Platform Contribution per Order

```
platform_contribution = customer_usdt_debit - agent_total_usdt - referral_cost_usdt

referral_cost_usdt = (if qualifying referral reward applies) reward_usdt else 0
```

**Example:**
```
customer_usdt_debit   = 54.64480874
agent_total_usdt      = 55.76923077   ← NOTE: contribution can be negative!
referral_cost_usdt    = 0

platform_contribution = 54.64480874 - 55.76923077 = -1.12442203 USDT  ← LOSS
```

> ⚠️ **Warning:** The admin profitability calculator must highlight when rate configuration produces negative platform contribution. This is not blocked by the system but requires explicit acknowledgement.

**Correct configuration example (customer_rate > agent_rate + commission spread):**
```
customer_rate = 91.50, agent_rate = 90.00, commission 1.50%
customer_usdt_debit = 5000 / 91.50 = 54.64480874
agent_total_usdt    = (5000/90) + (75/90) = 55.5556 + 0.8333 = 56.3889  ← still loss at this spread

For profit: customer_rate must exceed agent_rate × (1 + commission%) sufficiently
```

The admin profitability preview tool must model this explicitly with live values.

### 11.4 Referral Reward (Customer)

```
reward_usdt = settings.customer_referral_reward_usdt   (e.g. 1.00 USDT)
Trigger:      first completed payment order by referred customer
```

### 11.5 Agent Partner Reward

```
partner_reward_percent = settings.agent_partner_reward_percent  (e.g. 5%)
reward_usdt            = commission_usdt × partner_reward_percent / 100
Trigger:               each commission earned by referred agent
```

### 11.6 Rounding Rules

| Amount Type | Precision | Rounding |
|---|---|---|
| USDT amounts (display) | 4 dp | HALF_UP |
| USDT amounts (ledger) | 18 dp | exact |
| USDT amounts (settle) | 8 dp | HALF_UP |
| INR amounts | 2 dp | HALF_UP |
| Rates | 8 dp | exact |
| Percentages | 4 dp | exact |

```json
  "available_balance": "100.00000000",
  "remaining_after": "45.35519126",
  "expires_at": "ISO8601",
  "recipient_upi_id": "example@upi",
  "recipient_name": "John Doe"

```
**Note:** Quote does not reserve funds yet.

#### `POST /api/orders` — Confirm order (reserves funds)

**Auth:** Customer  
**Body:**
```json
{
  "quote_id": "uuid",
  "idempotency_key": "uuid-v4"
}
```
**Transaction (atomic):**
1. Validate quote not expired
2. Validate customer balance still sufficient
3. Create order record (status: FUNDS_RESERVED)
4. Create ledger reserve entries
5. Set order expiry timer

**Response 201:** Order object  
**Realtime:** `ORDER_CREATED` → `ORDER_RESERVED` → `ORDER_AVAILABLE`  
**Audit:** `ORDER_CREATED`

---

#### `POST /api/orders/:id/claim` — Agent claims order

**Auth:** AGENT (active, onboarding complete)  
**Body:**
```json
{ "idempotency_key": "uuid-v4" }
```
**Validation:**
- Order status must be `AVAILABLE`
- Agent status must be `ACTIVE`
- Agent not at max active orders
- Agent claims paused check
- **Atomic:** `UPDATE payment_orders SET status='ASSIGNED', agent_id=$1 WHERE id=$2 AND status='AVAILABLE'` — returns 0 rows if already claimed

**Response 200:** Order with assignment details  
**Response 409:** "Order no longer available"  
**Realtime:** `ORDER_ASSIGNED`  
**Notification:** Customer, agent  
**Audit:** `ORDER_CLAIMED`

---

#### `POST /api/orders/:id/payment` — Agent submits payment proof

**Auth:** AGENT (own order)  
**Body (multipart/form-data):**
```
agent_payment_ref: "UTR12345678901"
agent_payment_time: "ISO8601"
agent_payment_notes: "Paid via GPay"
proof: <file upload, optional>
idempotency_key: "uuid"
```
**Validation:**
- Order status must be `ASSIGNED`
- Agent must be order's assigned agent
- Order not expired
- File: image/PDF, max 5MB

**Response 200:** Updated order  
**Realtime:** `ORDER_PAYMENT_SUBMITTED`  
**Notification:** Manager alert  
**Audit:** `PAYMENT_SUBMITTED`

---

#### `POST /api/orders/:id/approve` — Manager approves payment

**Auth:** PAYMENT_REVIEWER, OPERATIONS_MANAGER  
**Body:**
```json
{
  "checklist_confirmed": true,
  "notes": "UTR verified via bank statement",
  "idempotency_key": "uuid-v4"
}
```
**Transaction (atomic):**
1. Validate order status = `PAYMENT_SUBMITTED` or `MANAGER_REVIEW`
2. Update order → `APPROVED` → `COMPLETED`
3. Debit customer reserved balance
4. Credit agent pending balance
5. Create settlement record
6. Create commission record
7. Post agent settlement ledger entries
8. Process referral reward if applicable
9. Update order → `AGENT_SETTLEMENT_POSTED` → `COMMISSION_POSTED`

**Response 200:** Completed order + settlement  
**Realtime:** `ORDER_COMPLETED`, `AGENT_SETTLEMENT_PENDING`  
**Notification:** Customer (payment confirmed), Agent (settlement pending review)  
**Audit:** `PAYMENT_APPROVED`, `SETTLEMENT_POSTED`

---

#### `POST /api/orders/:id/reject`

**Auth:** PAYMENT_REVIEWER, OPERATIONS_MANAGER  
**Body:**
```json
{
  "reason": "UTR not verifiable",
  "idempotency_key": "uuid-v4"
}
```
**Transaction (atomic):**
1. Update order → `REJECTED`
2. Release customer reserved funds → available
3. Order re-enters marketplace or refunds

**Audit:** `PAYMENT_REJECTED`

### 18.7 Telegram Service Implementation

```typescript
// lib/telegram/service.ts
export class TelegramService {
  private baseUrl: string;
  private token: string;

  constructor() {
    this.token = process.env.TELEGRAM_BOT_TOKEN!;
    this.baseUrl = `https://api.telegram.org/bot${this.token}`;
  }

  async sendMessage(chatId: number, text: string, options?: {
    parse_mode?: 'HTML' | 'MarkdownV2';
    reply_markup?: object;
  }): Promise<void> {
    const response = await fetch(`${this.baseUrl}/sendMessage`, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ chat_id: chatId, text, ...options }),
    });
    if (!response.ok) {
      const error = await response.json();
      throw new Error(`Telegram API error: ${JSON.stringify(error)}`);
    }
  }

  async setWebhook(url: string, secret: string): Promise<void> {
    await fetch(`${this.baseUrl}/setWebhook`, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ url, secret_token: secret }),
    });
  }
}
```

## 20. Referral System

### 20.1 Customer Referral

**Referral code:** 8-character alphanumeric, auto-generated on profile creation.  
`referral_code = nanoid(8).toUpperCase()`

**Referral link:** `https://tetherpay.fun/register?ref=CODE`

**Attribution:** On registration with ref code:
- Create `referral_relationships` record
- `relationship_type = 'CUSTOMER'`

**Reward trigger:** First completed payment order by referred customer.

**Reward flow:**
1. Order completes
2. System checks if customer has a referrer
3. Checks `referral_rewards` for same trigger event (idempotency)
4. Creates pending reward
5. Admin approves batch of pending rewards
6. Credit to referrer's account via ledger

**Reward amount:** `settings.customer_referral_reward_usdt` (default: 1.00 USDT)

### 20.2 Agent Partner Referral

**Referral code:** Separate partner code for each agent.  
**Attribution:** When a new agent registers using the partner link.

**Reward trigger:** Each commission earned by referred agent.  
**Reward amount:** `commission_usdt × agent_partner_reward_percent / 100`

**Financial note:** Partner reward is a cost to platform, not taken from referred agent's commission.

### 20.3 Anti-Fraud Rules

Checks applied at referral attribution and reward approval:

1. **Self-referral:** `referrer_id != referred_id` — DB constraint
2. **Same IP at registration:** Flag for review (not auto-block)
3. **Same device fingerprint:** Flag for review
4. **Same email pattern:** Flag if email domain same as referrer
5. **Duplicate account:** Cross-reference phone/KYC
6. **Circular referral:** A → B → A not permitted; depth = 1 max
7. **Suspicious velocity:** >10 referrals in 24h → auto-flag

All flagged referrals: `fraud_flagged = true`, reward held `PENDING` until admin approves.

### 20.4 Admin Referral Controls

- Enable/disable referral system globally
- Configure reward amounts
- Configure qualification criteria
- View fraud-flagged referrals
- Approve/reject individual rewards
- Reverse credited rewards (if fraud detected post-credit)

```
  ↓
```

## 23. Treasury & Reconciliation

### 23.1 Treasury Model

The web application stores:
- Public wallet addresses
- Manual balance observations
- Accounting ledger

The web application does **NOT** store:
- Private keys
- Seed phrases
- Wallet passwords

**Custody boundary:** Private key management is external (hardware wallet, qualified custodian, or authorized personnel's offline process). The application records the result of treasury operations.

### 23.2 Reconciliation Formula

```
Expected Balance = 
    SUM(customer available balances)
  + SUM(customer reserved balances)
  + SUM(agent available balances)
  + SUM(agent pending balances)
  + SUM(agent withdrawal reserved balances)
  + platform_revenue
  + platform_float

Observed Balance = manually entered from blockchain/wallet

Reconciliation Status:
  MATCHED   if |observed - expected| < tolerance (e.g. 0.001 USDT)
  MISMATCH  otherwise
```

### 23.3 Daily Reconciliation Workflow

1. Treasury admin opens `/admin/reconciliation`
2. Inputs today's observed wallet balance
3. System calculates expected balance from ledger
4. Shows MATCHED or MISMATCH
5. If MISMATCH: creates reconciliation case, Telegram admin alert
6. Admin investigates and notes findings
7. Resolution recorded in audit log

**PRODUCTION INFRASTRUCTURE REQUIREMENT:** Automated blockchain balance monitoring should be implemented before significant public-money scale. The current model relies on manual observation.

### 24.4 Profitability Calculator (Admin)

```typescript
function calculatePlatformContribution(params: {
  inrAmount: Decimal;
  customerRate: Decimal;
  agentRate: Decimal;
  commissionRate: Decimal;
  platformFeePercent: Decimal;
  platformFeeFlat: Decimal;
  referralCostUsdt: Decimal;
}) {
  const feeInr = params.inrAmount.mul(params.platformFeePercent.div(100))
                   .add(params.platformFeeFlat);
  const totalInr = params.inrAmount.add(feeInr);
  const customerDebit = totalInr.div(params.customerRate);

  const baseUsdt = params.inrAmount.div(params.agentRate);
  const commissionUsdt = params.inrAmount.mul(params.commissionRate.div(100))
                           .div(params.agentRate);
  const agentTotal = baseUsdt.add(commissionUsdt);

  const contribution = customerDebit.sub(agentTotal).sub(params.referralCostUsdt);
  const contributionPercent = contribution.div(customerDebit).mul(100);

  return {
    customerDebit,
    agentTotal,
    contribution,
    contributionPercent,
    isNegative: contribution.lt(0),
  };
}
```

Admin UI shows live preview with warning banner when contribution is negative.

## 25. Security Architecture

### 25.1 Threat Model

| Threat | Mitigation |
|---|---|
| Account takeover | Password hashing (Supabase), 2FA, login alerts, session management |
| Balance manipulation | No direct balance mutations, ledger-only, DB constraints |
| Double-spend | TX hash unique index, idempotency keys |
| IDOR | RLS policies per user/role |
| CSRF | Same-site cookies, CSRF tokens for mutations |
| XSS | React escaping, CSP headers |
| SQL injection | Parameterized queries (Supabase client) |
| Secret exposure | Server-only env vars, never NEXT_PUBLIC_ for secrets |
| Webhook replay | Telegram update_id deduplication, secret header |
| Admin privilege escalation | Role stored in DB, not JWT claims only |
| File upload attacks | MIME validation, size limits, private bucket |
| Rate abuse | Rate limiting on all sensitive endpoints |

### 29.2 Financial Invariant Tests

```typescript
// tests/unit/financial/invariants.test.ts

describe('ledger double-entry invariant', () => {
  it('sum of debits equals sum of credits for every transaction', async () => {
    const { data: transactions } = await supabase
      .from('ledger_transactions').select('id');
    
    for (const tx of transactions!) {
      const { data: entries } = await supabase
        .from('ledger_entries')
        .select('direction, amount')
        .eq('transaction_id', tx.id);
      
      const debits = entries!
        .filter(e => e.direction === 'DEBIT')
        .reduce((s, e) => s.add(e.amount), new Decimal(0));
      const credits = entries!
        .filter(e => e.direction === 'CREDIT')
        .reduce((s, e) => s.add(e.amount), new Decimal(0));
      
      expect(debits.toFixed(18)).toBe(credits.toFixed(18));
    }
  });
});

describe('balance non-negativity invariant', () => {
  it('all account balances are >= 0', async () => {
    const { data: balances } = await supabase
      .from('account_balances').select('*');
    
    for (const b of balances!) {
      expect(new Decimal(b.available).gte(0)).toBe(true);
      expect(new Decimal(b.reserved).gte(0)).toBe(true);
      expect(new Decimal(b.pending).gte(0)).toBe(true);
    }
  });
});
```

### 30.1 Deposit Operator Workflow

**Daily task:** Clear the deposit verification queue.

```
1. Navigate to /ops/deposits
2. Sort by: Oldest first
3. For each pending deposit:
   a. Click "Review"
   b. Read the deposit request:
      - Customer ID
      - Expected amount + network
      - Submitted TX hash
   c. Open blockchain explorer link (Tronscan for TRON)
   d. Verify:
      ✓ Transaction exists on blockchain
      ✓ Network matches (TRON/TRC-20)
      ✓ Token is USDT (not TRX or other)
      ✓ Destination address matches our central wallet
      ✓ Amount matches (note any variance)
      ✓ Transaction is confirmed (not pending)
      ✓ TX hash not in any other credited deposit
   e. Check every box on the verification checklist
   f. Enter received amount (if different from expected)
   g. Add reviewer notes
   h. Click "Approve"
   i. System credits customer balance
   j. Customer receives notification
4. If any check fails → Reject with reason
5. If suspicious → Escalate with notes
6. End of day: confirm queue is clear
```

## 33. AI Coding Guide

### 33.1 Absolute Rules

```
DO NOT invent new database tables without updating this PRD.
DO NOT bypass Row Level Security policies.
DO NOT directly edit account_balances table from frontend code.
DO NOT use JavaScript native number/float for financial calculations.
DO NOT put SUPABASE_SERVICE_ROLE_KEY or TELEGRAM_BOT_TOKEN in NEXT_PUBLIC_ variables.
DO NOT add financial behavior without corresponding ledger entries.
DO NOT bypass state machine validations.
DO NOT bypass audit logging on financial or sensitive operations.
DO NOT silently change financial formulas without updating the PRD formula section.
DO NOT modify critical business rules without a corresponding PRD update.
DO NOT skip idempotency keys on financial mutation endpoints.
DO NOT assume authenticated = authorized (always check role and resource permission).
DO NOT log sensitive financial values or credentials in application logs.
DO NOT create balance adjustments without the manual adjustment API + second approval where required.
```

```
5. Add or update tests for the changed behavior.
6. Update this PRD if behavior changes.
```

## Appendix C: Incident Response Procedures

### C.1 Treasury Mismatch

```
Detection:    Automated reconciliation shows MISMATCH
Immediate:    Treasury admin alerted via Telegram
              Pause new withdrawals (emergency control)
Investigation: Review all ledger entries since last MATCHED reconciliation
              Identify discrepancy source
              Check for off-ledger operations
Resolution:   Correct ledger via manual adjustment (requires approval)
              Document in reconciliation case
              Restore normal operations
Post-incident: Review process for prevention
```

### C.2 Suspected Account Takeover

```
Detection:    Unusual login location, security event
Immediate:    Freeze affected account
              Revoke all active sessions
Alert:        User notification via Telegram/email
Investigation: Review audit log for recent actions
               Check for unauthorized transactions
Resolution:   Coordinate with user for identity verification
              Restore account after verification
              Reverse any unauthorized transactions via manual adjustment
```

### C.3 Duplicate Deposit Credit

```
Detection:    Idempotency check failure, reconciliation mismatch
Immediate:    No customer-facing action until verified
Investigation: Review both deposit records
              Verify blockchain TX
Resolution:   Apply manual adjustment to reverse duplicate credit
              Requires two approvals
              Full audit trail required
```

### C.4 Compromised Admin Account

```
Immediate:    Revoke all sessions for compromised account
              Disable account
              Alert OWNER/SUPER_ADMIN
              Freeze all pending approvals from that account
Investigation: Audit log review of all actions in past 72h
              Identify any unauthorized approvals
Resolution:   Reverse unauthorized actions via adjustment workflow
              Re-enable account after credential reset and 2FA re-enrollment
              Security review
```
