    93→    93→## 2. Assumptions & Decisions
    94→    94→
    95→    95→| # | Decision | Rationale |
    96→    96→|---|---|---|
    97→    97→| A1 | Single Next.js monorepo with role-based routing | Faster to build, separable later |
    98→    98→| A2 | pnpm as package manager | Faster installs, better workspace support |
    99→    99→| A3 | Node.js 20 LTS | Stable, supported, matches Netlify defaults |
   100→   100→| A4 | Supabase Auth for all authentication | Reduces external service dependencies |
   101→   101→| A5 | Central USDT wallet model (not per-user wallet) | Matches stated business requirement |
   102→   102→| A6 | Manual payment verification first (no automated chain monitoring) | Matches stated business model |
   103→   103→| A7 | PostgreSQL numeric(38,18) for all financial amounts | Safe decimal precision |
   104→   104→| A8 | HALF_UP rounding on displayed/settled amounts | Standard financial rounding |
   105→   105→| A9 | Supabase Realtime via PostgreSQL replication | Free tier compatible |
   106→   106→| A10 | Telegram as notification-only, not authorization | Security boundary |
   107→   107→| A11 | TRON (TRC-20) as primary USDT network | Lowest fees for USDT transfers; others configurable |
   108→   108→| A12 | UPI as sole INR payment method | Matches stated product scope |
   109→   109→| A13 | 1-level referral depth for financial rewards | Anti-MLM requirement |
   110→   110→| A14 | Orders expire after 10 minutes (configurable) | Backend-controlled, configurable |
   111→   111→| A15 | All sensitive files in Supabase private buckets | Security requirement |
   112→   112→| A16 | No direct balance field mutations from frontend | Ledger-only financial state |

   116→   116→## 3. Business Model
   117→   117→
   118→   118→### 3.1 Operational Flow
   119→   119→
   120→   120→```
   121→   121→CUSTOMER
   122→   122→    │
   123→   123→    │  deposits USDT to central wallet
   124→   124→    ▼
   125→   125→CENTRAL TETHERPAY USDT WALLET
   126→   126→    │
   127→   127→    │  manager manually verifies on-chain
   128→   128→    ▼
   129→   129→CUSTOMER INTERNAL USDT LEDGER (credited)
   130→   130→    │
   131→   131→    │  customer creates INR payment order
   132→   132→    │  (USDT reserved from available balance)
   133→   133→    ▼
   134→   134→PAYMENT ORDER MARKETPLACE (AVAILABLE state)
   135→   135→    │
   136→   136→    │  agent views and claims order
   137→   137→    ▼
   138→   138→AGENT
   139→   139→    │
   140→   140→    │  agent pays recipient via own UPI channel
   141→   141→    │  (agent uses personal INR funds)
   142→   142→    ▼
   143→   143→UPI RECIPIENT (payment received in INR)
   144→   144→    │
   145→   145→    │  agent submits: UTR / reference / screenshot
   146→   146→    ▼
   147→   147→MANAGER
   148→   148→    │
   149→   149→    │  manually verifies payment
   150→   150→    ▼
   151→   151→    ├── REJECTED → order re-enters marketplace or refunded
   152→   152→    └── APPROVED
   153→   153→           │
   154→   154→           ▼
   155→   155→    AGENT USDT SETTLEMENT
   156→   156→    (reimbursement + commission credited to agent wallet)
   157→   157→           │
   158→   158→           │  agent requests USDT payout
   159→   159→           ▼
   160→   160→    ADMIN/TREASURY
   161→   161→    (manual USDT transfer to agent's external wallet)
   162→   162→```
   163→   163→
   164→   164→### 3.2 Revenue Model
   165→   165→
   166→   166→```
   167→   167→Customer pays:   INR amount + platform fee (converted to USDT debit)
   168→   168→Agent receives:  USDT equivalent of INR paid + commission
   169→   169→Platform earns:  Spread between customer rate and agent rate + fees - commissions
   170→   170→```
   171→   171→
   172→   172→### 3.3 Central Wallet Model
   173→   173→
   174→   174→```
   175→   175→Customer A ─┐
   176→   176→Customer B ─┼──▶ Central TetherPay USDT Wallet (single address per network)
   177→   177→Customer C ─┘
   178→   178→```
   179→   179→
   180→   180→- Customers send USDT to the **central wallet address**.
   181→   181→- Customers submit a deposit request with TX hash.
   182→   182→- Managers verify on-chain and approve/reject.
   183→   183→- The application's internal ledger is the source of truth for individual balances.

   258→   258→### 4.3 Financial Arithmetic
   259→   259→
   260→   260→**NEVER use JavaScript native `number` or `float` for financial amounts.**
   261→   261→
   262→   262→All financial calculations use `decimal.js`:
   263→   263→
   264→   264→```typescript
   265→   265→import Decimal from 'decimal.js';
   266→   266→
   267→   267→Decimal.set({ precision: 38, rounding: Decimal.ROUND_HALF_UP });
   268→   268→
   269→   269→// Agent settlement example
   270→   270→function calculateAgentSettlement(inrPaid: string, agentRate: string, commissionRate: string) {
   271→   271→  const inr = new Decimal(inrPaid);
   272→   272→  const rate = new Decimal(agentRate);
   273→   273→  const commission = new Decimal(commissionRate).div(100);
   274→   274→
   275→   275→  const baseUsdt = inr.div(rate);
   276→   276→  const commissionInr = inr.mul(commission);
   277→   277→  const commissionUsdt = commissionInr.div(rate);
   278→   278→  const totalUsdt = baseUsdt.add(commissionUsdt);
   279→   279→
   280→   280→  return {
   281→   281→    baseUsdt: baseUsdt.toFixed(8),
   282→   282→    commissionInr: commissionInr.toFixed(2),
   283→   283→    commissionUsdt: commissionUsdt.toFixed(8),
   284→   284→    totalUsdt: totalUsdt.toFixed(8),
   285→   285→  };
   286→   286→}
   287→   287→```
   288→   288→
   289→   289→All amounts stored in PostgreSQL as `numeric(38,18)`.
